# Plan: "Special Event - Welcome Session" on every attendance form

Ryan, 2026-10-13: a "Special Events" module that captures unique, ad-hoc sessions; the first type
is "Welcome Session".

## Context (read 2026-10-13, GETs and read-only SOQL only)
- **The chain.** Year q94 (`1|2|3`, required) shows the module dropdown of that year (q14 / q92 /
  q93, required, single-select, `calcValues` = their own options), which shows the session
  dropdown of the module's count (q15 / q95 / q96 / q97: 8 / 10 / 14 / 15 sessions, `calcValues`
  `|1|2|...`). Hidden q98 (`control_textbox`), q100 and q102 (`control_number`) copy module,
  session and year for the Salesforce mapping. All generated by `build_conditions` sections B
  and C (`sync_attendance_form.py:312-337`); year 1 has ONE rule, `YEAR equals 1 -> show q15`
  ("every year-1 module is 8 sessions"), years 2 and 3 one rule per module from
  `SESSION_OVERRIDES`. Module options are hand-kept on each form; the sync reads them live and
  writes only their `calcValues` (never unattended: `auto_sync.py` ATTENTION).
- **Salesforce** (`getObjectSchema`): `Attendance_Batch__c.Module__c` text(255),
  `Module_Week__c` and `Module_Year__c` double, none required; the same three on
  `Attendance__c`. `AttendanceBatchProcessor` (read 2026-10-13, last modified 2026-10-07 04:38
  UTC) only copies the three onto each row (`addAttendanceRecord`): a blank week is copied as
  blank. No batch since 2026-09-01 has a blank `Module_Week__c`, so a blank week through
  Jotform's Salesforce V2 integration is unproven.
- **One batch per club and date.** `isDuplicateBatch` (a `Success` batch for the account and
  date) and `hasAttendanceForClubOnDate` (any `Attendance__c` row for the account and date) each
  refuse a second batch: 42 `Failed` "Duplicate" since launch.

## Decisions (Ryan, 2026-10-13)
1. **A module option, not a new question.** The event is a module option named
   `Special Event - <type>` (as the electives are `Elective - <name>`), in every year's module
   dropdown, with no session dropdown. Salesforce receives `Module__c = "Special Event - Welcome
   Session"`, `Module_Week__c` blank, `Module_Year__c` the year. No new question, no Salesforce
   schema, mapping or Apex change. Rejected: a "Special Events" module opening a new "Event"
   dropdown (a new question on five forms whose qid would differ per form, and a new Salesforce
   field or a combined text anyway).
2. **The same-day rule stays.** A Welcome Session on a day the club also holds a curriculum
   session is refused as a duplicate (whichever arrives second); mentors submit one per day.
3. **All three years.**

## The change (branch `wf22/special-events`)
1. `glow/sync.py`: `SPECIAL_EVENT_PREFIX = "Special Event - "` and `SPECIAL_EVENTS =
   ("Welcome Session",)` (EDIT HERE to add a type), and a helper giving the option texts. Python
   only (like `SESSION_OVERRIDES`; Apps Script never reads modules).
2. **The sync owns the event options** (`sync_attendance_form.py`): every module dropdown (q14,
   q92, q93) ends with the `SPECIAL_EVENTS` options in that order; a missing one is appended after
   the curriculum options, written together with the dropdown's `calcValues` in one question
   write per dropdown. It never removes, renames or reorders an option; an option that starts
   with the prefix but is not in `SPECIAL_EVENTS` is a warning, left alone (removal is by hand:
   RUNBOOK). Rules are generated from the options the form will have after the write, so a dry
   run shows the whole result.
3. **Cascade (section B)**: year 1 gets one rule per module (`q14 equals m AND YEAR equals 1 ->
   show q15`) like years 2 and 3, replacing the single year rule; no event option shows a
   session dropdown in any year.
4. **Bridge (section C)**: when an event is the module, question 100 (`WEEK_ID`) is blank in
   the submission, also when the mentor first picked a curriculum module and a session and then
   switched to the event. The hidden session dropdown is cleared at submit
   (`clearFieldOnHide`), but q100 was already calculated from it. The mechanism (e.g. a
   calculation rule that empties q100 for an event, ordered so that it wins against the session
   copy rules: Jotform walks a field's rules last to first) is proven in the template's served
   page before any regional form. If Jotform cannot blank a number field by rule, stop and ask
   Ryan; 0 is not chosen silently.
5. **The runner** (`tools/auto_sync.py`): an event-option write is held like the module
   `calcValues` (ATTENTION, the region not applied), never applied unattended.
6. **The audit** (`tools/form_status.py`): every module dropdown carries each `SPECIAL_EVENTS`
   option once and its `calcValues` stays aligned; no rule shows a session dropdown for an
   event; the q100 clearing rule is present and in the order item 4 proved; `--rendered`: the
   event options served with their `data-calcvalue`. A form without the options yet is "awaiting
   apply", not CLEAN.
7. **Reading submissions** (`glow/submissions.py`): an event submission reads module = the event
   option, session = none, never `Unreadable`.
8. **Translations**: the option text is translated exactly as the existing module options are
   (if each form's translation store has entries for module options, the new option gets them in
   every language of that form, GET-merge-POST; if not, none). Drafts are listed in this plan's
   build notes for Ryan before any write.
9. **Tests** for each of 2-7; fixtures stay fictional. **Docs**: ARCHITECTURE (the cascade and
   the constants), RUNBOOK section "Special events" (add a type: one line plus translations,
   rolled out by hand template first; retire one: by hand, Salesforce history stays), DECISIONS
   dated 2026-10-13. `make check` passes.

   Merge with `/integrate`.

## Rollback
Per form, `restore_conditions.py --from` the snapshot puts the rules back; the options are
removed in the builder (questions and options are never deleted by tooling), then the sync's
`calcValues` follow. Merge a revert of the branch only once every form is rolled back.

## Consequences
- The dashboard's "Jotform Sessions by Module Last Month" shows the event as its own bar.
- The attendance rate (BACKLOG 58) must decide whether events count as sessions held; a report
  can exclude them with `Module__c` starting with `Special Event - `.
- `tools/fix_module_values.py` takes the template's module options as canonical: the event
  option is one more valid value.

## Risks
- A blank number through the Salesforce integration is unproven (rollout step 2 proves it on a
  Duplicate batch, which writes no rows).
- Any region is held by the runner from merge to its apply: roll out on the same day.

**Item 4: the session bridge, as built.** An empty-equation rule "event → question 100 = ''" was
not chosen: it would have left question 100 blank when a mentor switches from the event back to a
module whose session dropdown still shows its old pick (the copy runs only when the session
dropdown changes), and Jotform's `runAllCalculations` skips a calculation with an empty equation.
Instead one more calculation into question 100 recomputes it from the session dropdown SHOWN:

- type `calculation`, link Any, terms `isFilled` on q94, q14, q92, q93, q15, q95, q96, q97;
  action `resultField` 100, equation `{15}{95}{96}{97}`, `ignoreHiddenFields` true, operands
  `94,14,92,93,15,95,96,97` (`glow/sync.py` `WEEK_BRIDGE_FIELDS`, `week_bridge_equation`);
- placed first in section B: after the roster rules (and question 18's rule 0), before every rule
  that shows a session dropdown and before the four copies `week_qid isFilled → 100`, which stay.
  On the template it is rule 366 of 400; the session rules start at 370, the copies are 395-398.

What it assumes, read 2026-10-13 in the template's served page and its runtime
(`jotform.forms.js` build `f4bbef18bb2`, md5 `13fc45a826`), the same mechanism as question 18's
sum (rule 0, ignore hidden fields, an operand outside the equation), live since 2026-10-02:

- `setConditions` reverses the rules; `runConditionForId` runs a field's rules in that order, so the
  bridge runs after the session rules and the copy in the walk of every field it tests; its
  operands' `change` listeners (a select: `change` on its `<li>`) run it once more after them.
  `runAllConditions` (load, and 1.5 s later) dispatches each tested field's event in turn; every
  field a rule into question 100 tests is one of the bridge's terms, so whichever walk comes last
  ends with the bridge: on a restored page it has the last word too.
- `checkCalculation` writes a number field (`case "number"`) as its output with everything but
  `-0-9.` stripped: "" empties question 100. A calculation runs only while its condition is true;
  with the year picked it is.
- `ignoreHiddenFields`: an operand whose `<li>` (or section) has `form-field-hidden` contributes "".
  The template serves q15, q95, q96 and q97 with `form-field-hidden` (and `always-hidden`) until a
  rule shows them; `showField` removes both.
- A select operand reads its chosen option's `data-calcvalue` (the session numbers); the "Please
  Select" placeholder (`value=""`) reads "" because the page sets `JotForm.newDefaultTheme = true`
  (else its text would be read and stripped to "" by the number field anyway).
- Question 100's input is inside `.always-hidden`, so it is not "typeable": every operand change
  recomputes it (no snapshot shortcut).
- A calculation whose condition turns false clears its result field after 50 ms unless another
  calculation for that field is true - the bridge's condition is true whenever a year is picked,
  so a copy turning false clears nothing.
